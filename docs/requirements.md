# 포트폴리오 요구사항 및 작성 원칙 확정

## 1. 목적 및 범위

이번 포트폴리오는 공학작문 및 발표 과제 6의 요구사항을 충족하는 동시에, 향후 게임 업계 취업을 위해 지속적으로 갱신하고 활용할 수 있는 개인 포트폴리오를 구축하는 것을 목적으로 한다.

09번 강의자료의 직무 역량 증명, 10번 강의자료의 Markdown 기반 문서 작성 및 정적 사이트 배포, 11번 강의자료의 문서 작성 및 변경 관리 원칙을 주요 기준으로 삼는다.

| 구분 | 확정 사항 |
|---|---|
| 닉네임 | KimJ6 |
| 현재 관심 분야 | 게임 클라이언트 개발 및 게임 기획 (주요 관심 기술: Unity) |
| GitHub | [github.com/KimJ6](https://github.com/KimJ6) |
| 주 독자 | 게임 개발 및 기획 직군의 채용 담당자, 실무자 |
| 부 독자 | 과제 평가자 |
| 작성 목적 | 프로젝트 경험을 통한 직무 역량 증명 |
| 관리 목적 | 지속적인 콘텐츠 추가, 수정 및 변경 이력 관리 |
| 작성 언어 | 한국어, 필요한 기술 용어는 영어 병기 |
| 콘텐츠 원본 | Markdown |
| 배포 형식 | 정적 웹사이트 |
| 배포 플랫폼 | GitHub Pages |

과제 평가자를 대상으로 별도의 학습 보고서를 작성하는 것이 아니라, **실제 채용 담당자가 열람할 수 있는 포트폴리오를 작성하고 이를 과제 결과물로 제출**하는 것을 기본 방향으로 확정한다.

## 2. 요구사항 확정

### 2.1. 과제 요구사항

과제에서 명시한 요구사항과 `+`로 표시한 추가 항목을 구분한다. 추가 항목도 실제 포트폴리오의 활용 가치를 고려하여 가능한 범위에서 충족하도록 한다.

| ID | 요구사항 | 구분 | 충족 기준 |
|---|---|---|---|
| A-01 | 닉네임 | 필수 | KimJ6 명시 |
| A-02 | 현재 관심 분야 | 필수 | Unity, 게임 클라이언트 개발 및 기획 명시 |
| A-03 | GitHub 링크 | 필수 | 개인 GitHub 프로필 연결 |
| A-04 | 대표 프로젝트 | 필수 | 최소 1개 이상의 프로젝트 소개 |
| A-05 | 문제 정의 | 필수 | 프로젝트에서 해결하려는 문제 명시 |
| A-06 | 역할 | 필수 | 본인의 책임과 기여 범위 명시 |
| A-07 | 기술 | 필수 | 프로젝트에 활용한 기술 명시 |
| A-08 | 결과 | 추가 | 실제 구현 또는 검증한 결과 제시 |
| A-09 | 데모 링크 | 추가 | 이용 가능한 실행 결과물 연결 |
| A-10 | 소스 코드 링크 | 추가 | 공개 가능한 저장소 연결 |
| A-11 | 이력서 PDF | 추가 | 다운로드 가능한 공개용 이력서 제공 |
| A-12 | GitHub Pages 배포 | 필수 | 공개 웹사이트 접속 가능 |
| A-13 | 과제 제출 | 필수 | URL만 포함한 지정 형식의 TXT 파일 제출 |

데모와 소스 코드가 존재하지 않거나 공개할 수 없는 경우에는 해당 링크를 억지로 제공하지 않는다.

### 2.2. 콘텐츠 요구사항

09번 강의자료에서는 포트폴리오를 자신의 능력을 주장하는 수단이 아니라 증명하는 수단으로 정의한다. 직무 관련성, 경험과 과정, 기술 선택 이유, 결과물 및 인사이트를 주요하게 다룬다.

이를 반영하여 다음 요구사항을 추가한다.

| ID | 요구사항 | 충족 기준 |
|---|---|---|
| C-01 | 직무 관련성 | 각 프로젝트가 목표 직무의 어떤 역량을 보여주는지 명확해야 함 |
| C-02 | 개발자상 | 자기소개와 프로젝트 경험이 일관된 개발자상을 형성해야 함 |
| C-03 | 개인 기여도 | 팀의 성과와 개인의 기여를 구분해야 함 |
| C-04 | 문제 해결 과정 | 문제, 판단, 해결 방법의 관계가 드러나야 함 |
| C-05 | 기술 선택 근거 | 주요 기술의 선택 이유와 활용 방식이 드러나야 함 |
| C-06 | 증명 가능성 | 주요 역량과 성과에 확인 가능한 근거가 있어야 함 |
| C-07 | 개발 상태 | 설계, 구현, 검증, 배포 상태를 명확히 구분해야 함 |
| C-08 | 경험 및 인사이트 | 의미 있는 판단, 트레이드오프, 교훈을 전달해야 함 |
| C-09 | 정보 최신성 | 프로젝트의 설명이 실제 개발 상태와 일치해야 함 |
| C-10 | 기존 콘텐츠 활용 | 기존 포트폴리오의 유효한 내용과 자료를 재사용해야 함 |

모든 프로젝트에서 코드, 관리, 협업, 배포 경험을 전부 다룰 필요는 없다. 각 프로젝트의 특징과 실제 수행한 경험에 따라 강조할 역량을 선택한다.

### 2.3. 작성 및 관리 요구사항

10번 강의자료에서는 Markdown의 가독성, 버전 관리 적합성, 다양한 출력 형식으로의 변환 가능성을 강조한다. 11번 강의자료에서는 README를 통한 안내와 명확한 변경 목적, 작은 변경 범위, 구조화된 커밋을 강조한다.

| ID | 요구사항 | 충족 기준 |
|---|---|---|
| M-01 | Markdown 중심 작성 | 주요 포트폴리오 콘텐츠를 Markdown으로 작성 |
| M-02 | 내용과 표현의 분리 | 콘텐츠 수정 시 HTML이나 CSS 수정이 불필요해야 함 |
| M-03 | 정보의 단일 원본 | 동일한 정보를 여러 문서에 중복 작성하지 않음 |
| M-04 | 문서별 책임 분리 | 자기소개, 프로젝트, 이력서, 관리 문서의 책임 구분 |
| M-05 | 공통 서식 | 프로젝트 추가 시 기존 서식 재사용 가능 |
| M-06 | 독립적인 콘텐츠 관리 | 개별 프로젝트 문서의 추가, 수정, 삭제 가능 |
| M-07 | 관리 가이드 | README를 통해 실행, 수정, 배포 방법 파악 가능 |
| M-08 | 버전 관리 | Git으로 콘텐츠 및 구조의 변경 이력 추적 |
| M-09 | 변경 단위 관리 | 내용 변경과 표현 구조 변경을 가능한 한 분리 |
| M-10 | 출력 일관성 | 동일한 Markdown 구조에 동일한 표현 규칙 적용 |
| M-11 | 검증 가능성 | 문법, 링크, 빌드 결과를 검토할 수 있어야 함 |
| M-12 | 출력물 재현성 | 저장소의 원본을 기반으로 웹사이트를 다시 생성할 수 있어야 함 |

Markdown 사용 자체가 목적이 되어서는 안 된다. Markdown을 활용함으로써 작성과 검토가 쉬워지고, 콘텐츠의 수정 및 확장 비용이 감소해야 한다.

## 3. 작성 원칙 확정

### 3.1. 상위 원칙

강의자료에서 공통적으로 제시하는 3C 원칙과 포트폴리오의 증명 목적을 결합하여 여섯 가지 상위 원칙을 정의한다.

- **관련성 (Relevance):** 목표 직무와 관련된 경험과 정보를 중심으로 작성한다. 경험의 수보다 해당 경험이 증명하는 역량을 중시한다.
- **증명 가능성 (Verifiability):** 추상적인 역량 주장보다 수행한 작업, 판단 근거, 결과물로 역량을 증명한다.
- **명확성 (Clear):** 문제, 역할, 행동, 결과를 명확히 구분한다.
- **간결성 (Concise):** 핵심 정보를 우선하고 불필요한 설명, 반복, 수식어를 제거한다.
- **일관성 (Consistent):** 문서 간 용어, 문체, 정보 구조 및 표현 방식을 일관되게 유지한다.
- **유지보수성 (Maintainability):** 콘텐츠 추가와 수정이 다른 콘텐츠나 표현 구조의 불필요한 변경으로 이어지지 않도록 한다.

### 3.2. 콘텐츠 작성 원칙

| ID | 원칙 |

| P-02 | 모든 독자가 프로젝트의 배경이나 게임의 규칙을 알고 있다고 가정하지 않는다. |
| P-03 | 프로젝트의 핵심 가치와 본인의 기여를 앞부분에서 파악할 수 있도록 한다. |
| P-04 | 상세한 기술적 설명은 독자가 필요에 따라 추가로 열람할 수 있도록 구성한다. |

| ID | 원칙 |

| P-07 | 기술 스택의 나열보다 기술을 선택하고 활용한 이유를 중요하게 다룬다. |

| P-10 | 수치로 확인할 수 있는 성과는 측정 조건 및 비교 기준과 함께 제시한다. |

| 부적절한 표현 | 권장 표현 |
|---|---|

| 최적의 게임 밸런스를 설계했습니다. | 게임 밸런스를 조정할 수 있도록 주요 수치와 실행 로직을 분리했습니다. |
| 다양한 기술에 능숙합니다. | 프로젝트에서 해당 기술을 활용해 구현한 기능을 설명합니다. |

권장 표현 역시 실제 수행 사실에 부합할 때만 사용할 수 있다.

### 3.3. 문장 및 문단 작성 원칙

| ID | 원칙 |
|---|---|
| P-16 | 하나의 문장에는 하나의 핵심 주장을 담는다. |
| P-17 | 하나의 문단에는 하나의 주제와 정보 책임을 부여한다. |
| P-18 | 문단의 첫머리에 핵심 내용을 제시하고 이후 근거를 설명한다. |
| P-19 | 문장은 짧고 명확하게 작성하되 필요한 인과관계를 생략하지 않는다. |
| P-20 | 주어와 행위의 주체가 불명확한 표현을 지양한다. |
| P-21 | 객관적인 서술을 우선하고 과장된 수식어와 자기 평가를 지양한다. |
| P-22 | 동일한 개념에 동일한 용어를 사용한다. |
| P-23 | 기술 용어는 일반적으로 통용되는 명칭을 사용한다. |

| P-25 | 다른 영역에서 이미 전달한 정보는 불필요하게 반복하지 않는다. |

3C 원칙은 단순히 문장을 짧게 만드는 데 있지 않다. **독자가 필요한 정보를 적은 시간과 노력으로 정확하게 이해할 수 있도록 하는 것**이 목적이다.

| P-31 | 코드와 명령어는 인라인 코드 또는 코드 블록으로 구분한다. |
| P-32 | 링크의 표시 텍스트에 연결 대상과 목적을 명시한다. |
| P-33 | 표는 정형 정보와 단순 비교에 사용하고 긴 설명은 문단으로 작성한다. |
| P-34 | 이미지에는 내용을 설명하는 대체 텍스트를 작성한다. |
| P-35 | 강조 표기는 핵심 용어와 중요한 정보에 한정한다. |
| P-36 | Markdown 본문에 표현 목적의 HTML, CSS 사용을 최소화한다. |
| P-37 | CommonMark 및 GFM을 우선하며 렌더링 환경 간 호환성을 고려한다. |

YAML Front Matter는 Markdown 자체의 표준 문법은 아니지만, 문서의 메타데이터를 구조화하기 위한 정적 사이트 생성기의 기능으로 활용할 수 있다.

### 3.5. 정보 표현 원칙

| 정보 유형 | 권장 표현 | 적용 대상 |
|---|---|---|
| 핵심 주장 | 제목, 짧은 요약 | 개발자상, 프로젝트 핵심 가치 |
| 정형 정보 | 메타데이터, 표 | 개발 기간, 역할, 기술, 상태 |
| 논리적 설명 | 문단 | 문제 정의, 설계 판단, 인사이트 |
| 병렬적 정보 | 목록 | 주요 구현 기능, 기여 사항 |
| 실제 결과물 | 스크린샷, 영상 | 게임 실행 화면, 개발 결과 |
| 구조 및 관계 | 다이어그램 | 시스템 구조, 데이터 흐름 |
| 정량적 결과 | 표, 차트 | 성능 측정 및 비교 결과 |
| 상세 근거 | 링크 | 저장소, 논문, 설계 문서, 데모 |

표현 형식은 정보의 성격에 따라 결정한다. 시각적 다양성을 확보하기 위해 불필요한 표, 이미지, 그래프를 추가하지 않는다.

특히 게임 포트폴리오의 스크린샷은 단순 장식이 아니라 구현한 기능과 실제 결과물을 증명하는 자료로 활용한다.

### 3.6. 문서 관리 원칙

11번 강의자료의 README와 PR 관련 원칙을 개인 포트폴리오의 관리 방식에 맞게 적용한다.

| ID | 원칙 |
|---|---|
| P-38 | 모든 문서는 명확한 목적과 정보 책임을 가져야 한다. |
| P-39 | 동일한 정보는 하나의 원본에서 관리하고 다른 영역에서는 이를 참조한다. |
| P-40 | 프로젝트 문서는 공통 서식을 따르되 불필요한 항목을 강제하지 않는다. |
| P-41 | README는 포트폴리오 저장소의 사용 및 관리 가이드로 작성한다. |
| P-42 | 콘텐츠의 원본과 빌드된 결과물을 구분한다. |
| P-43 | 변경 목적과 영향 범위를 확인할 수 있도록 커밋을 작성한다. |
| P-44 | 콘텐츠 수정, 구조 변경, 디자인 변경은 논리적인 작업 단위로 분리한다. |
| P-45 | 문서 구조의 변경이 필요한 경우 세부 내용 수정에 앞서 구조를 검토한다. |
| P-46 | 공개 전에 문법, 링크, 개인정보 및 콘텐츠의 정확성을 검증한다. |
| P-47 | AI를 활용한 수정에서도 기존 문서의 정보 책임과 작성 원칙을 유지한다. |

개인 포트폴리오라는 규모를 고려하여 모든 수정에 이슈나 PR 작성을 강제하지 않는다. 관리 체계의 복잡성 자체가 유지보수 비용을 증가시키지 않도록 한다.

## 4. 이력서와 포트폴리오의 역할 구분

09번 강의자료의 이력서와 포트폴리오에 관한 정의를 반영하여 두 결과물의 정보 책임을 구분한다.

| 구분 | 이력서 | 포트폴리오 |
|---|---|---|
| 목적 | 지원자의 기본 자격 및 경험 전달 | 직무 수행 역량 증명 |
| 핵심 질문 | 어떤 경험과 자격을 보유했는가? | 실제로 무엇을 어떻게 수행할 수 있는가? |
| 주요 정보 | 경험, 기술, 성과 (학력 및 어학 제외) | 문제, 역할, 판단, 과정, 결과 |
| 서술 방식 | 정형화된 정보와 요약 | 근거를 포함한 설명 |
| 열람 방식 | 빠른 검토 | 선택적 상세 열람 |
| 배포 형식 | PDF | 정적 웹사이트 |
| 원본 관리 | Markdown | Markdown |

포트폴리오 웹사이트에 이력서의 모든 내용을 반복하여 작성하지 않는다. 반대로 이력서에 개별 프로젝트의 상세한 설계 및 개발 과정을 모두 담지 않는다.

공통 정보는 가능한 한 동일한 원본을 참조하도록 하며, 공개용 이력서에서는 불필요한 개인정보를 제외한다.

## 5. 작업 범위 및 제외 사항

과제의 완성도와 향후 활용 가치를 확보하되 불필요하게 작업 규모가 확대되지 않도록 범위를 확정한다.

| 작업 대상 | 결정 |
|---|---|
| 기존 포트폴리오 콘텐츠 검토 및 개선 | 포함 |
| 대표 프로젝트 추가 및 갱신 | 포함 |
| Markdown 기반 콘텐츠 관리 구조 | 포함 |
| 문서별 정보 책임과 공통 서식 | 포함 |
| 기존 디자인 및 시각 자료 재사용 | 우선 적용 |
| 정적 사이트 생성 | 포함 |
| README 및 작성 가이드 | 포함 |
| 공개용 이력서 PDF | 포함 |
| GitHub Pages 배포 | 포함 |
| 기본적인 문법 및 링크 검증 | 포함 |
| 대규모 디자인 개편 | 필요성이 확인될 경우만 |
| 복잡한 애니메이션 및 인터랙션 | 원칙적으로 제외 |
| 관리자 페이지 및 CMS | 제외 |
| 백엔드 및 데이터베이스 | 제외 |
| 다국어 지원 | 현 단계 제외 |
| 기술 블로그 구축 | 현 단계 제외 |
| 프로젝트 자체의 추가 개발 | 제외 |

기술적 구현은 콘텐츠의 작성과 전달, 관리에 기여해야 한다. 포트폴리오 웹사이트 개발 자체가 본래의 게임 개발 및 기획 포트폴리오 작성보다 큰 작업이 되지 않도록 한다.

## 6. 평가 및 완료 기준

공식적인 과제 채점표가 아닌, 이번 작업의 자체적인 검수 기준이다.

| 평가 영역 | 핵심 평가 질문 |
|---|---|
| 과제 적합성 | 명시된 필수 요구사항을 모두 충족하는가? |
| 직무 적합성 | 게임 클라이언트 개발 및 기획 직무와의 관련성이 명확한가? |
| 증명 가능성 | 제시한 역량을 실제 경험과 결과물로 확인할 수 있는가? |
| 논리적 구조 | 문제, 역할, 판단, 수행 내용, 결과의 관계가 명확한가? |
| 가독성 | 독자가 원하는 정보를 빠르게 찾아 이해할 수 있는가? |
| 간결성 | 불필요하거나 반복되는 내용이 제거되었는가? |
| 일관성 | 문서 구조, 용어, 문체, 시각적 표현이 일관적인가? |
| 유지보수성 | Markdown을 수정하는 것만으로 주요 콘텐츠를 갱신할 수 있는가? |
| 확장성 | 기존 구조를 크게 수정하지 않고 프로젝트를 추가할 수 있는가? |
| 배포 품질 | 공개 웹사이트와 관련 자료가 정상적으로 열람되는가? |

## 7. 적용 및 관리

상위 기준 문서로 지속 적용한다. [정보 구조](information-architecture.md)와 [Markdown 서식](markdown-specification.md)을 함께 참고한다.

원본: 프로젝트 소스에 등록된 요구사항 및 작성 원칙 v1.0. 저장소용 Markdown으로 변환하며 화면 구성용 UI와 완료 체크리스트를 제거했다. 관심 분야는 후속 사용자 지시에 따라 게임 클라이언트 개발 및 게임 기획, 주요 관심 기술 Unity로 구분한다.

## 사용자 확정 사항 (웹사이트 v1.2)

공개용 포트폴리오와 이력서에는 학력 및 어학 정보를 포함하지 않는다. 프로젝트의 표시 순서는 최초 HTML의 기존 프로젝트 상대적 순서를 유지하며, 사용자 요청에 따라 PinShift를 메트로놈 앞에 추가한다. 현재 순서는 렌더링 연구, Drilling, OverTheHorizon, PinShift, PrecisionTick Metronome이며 사용자 요청 없이 변경하지 않는다. 이 사항은 이전 설계 및 검수 기록보다 우선한다.
